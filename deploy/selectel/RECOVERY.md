## Сервер и Coolify

Предлагаемая стартовая конфигурация для сборки Next.js, PostgreSQL и Coolify на одном сервере: Ubuntu 24.04 LTS, 4 vCPU, 8 GB RAM, SSD 80 GB. Это выбор конфигурации для старта, не результат нагрузочного тестирования. Окончательная стоимость проверяется в панели Selectel до создания сервера.

1. Создать сервер Selectel и настроить SSH-доступ. Получить фактический IP и проверить SSH, ОС и свободное место.
2. Установить Coolify по официальной инструкции. Выполнять команды только на новом сервере. Создать учётную запись владельца и настроить HTTPS для панели.
3. Создать отдельный проект 10coffee и PostgreSQL 18 с постоянным диском. Не публиковать порт PostgreSQL в Интернет. Сохранить внутренний URL БД приватно.
4. Перед переносом проверить SHA256 дампа по `manifest.json`. Передать дамп и архив файлов на новый сервер по SSH. Не размещать их в `public`, `media`, Git или общедоступном HTTP-каталоге.

Официальные инструкции: [создание сервера Selectel](https://docs.selectel.ru/cloud-servers/create/create-server/), [установка Coolify](https://coolify.io/docs/start-with-self-hosted), [восстановление PostgreSQL](https://coolify.io/docs/databases/restore).

## Восстановление базы

1. Проверить, что выбрана новая пустая БД сайта, а не служебная БД Coolify.
2. От имени администратора новой PostgreSQL выполнить `pre-restore.sql`: политике RLS из дампа требуется роль `authenticated`. Создаётся роль без права входа, без пароля и без выдачи привилегий.
3. Восстановить custom-дамп с `pg_restore --no-owner --no-acl --exit-on-error --single-transaction`. Доступ задавать через приватное окружение, не печатать строку подключения или пароль в командах и журналах.
4. Выполнить `post-restore.sql` на новой БД: отключить оплату в глобальных настройках и проверить контрольные количества. Исходный дамп сохраняется неизменным.
5. Выполнить `npm run payload:migrate:status`, затем при необходимости явный `npm run payload:migrate`. Нельзя просто применять текущие миграции к пустой БД: они предполагают существование исходных таблиц.

Резервная копия Coolify отдельно не найдена. Coolify устанавливается заново: его собственная копия не заменяет копию БД приложения или файлов.

## Приложение

1. Подключить фактический Git-репозиторий и ветку `shop`, проверить commit. Для восстановления использовать Nixpacks с Node.js 22, `npm ci`, `npm run build`, `npm start`; порт приложения 3000. Это сохраняет включение планировщика через штатную команду старта. Фактическую сборку на новом сервере проверить по журналу.
2. Настроить переменные из `production.env.example`. `DATABASE_URL` и `PAYLOAD_SECRET` нужны при сборке и при запуске. Секреты заполняются приватно в Coolify. Не подставлять localhost вместо внутреннего URL новой PostgreSQL.
3. Для локального хранения загрузок настроить постоянные каталоги `/app/media`, `/app/job-application-files`, `/app/public/uploads/avatars`; проверить реальный рабочий каталог образа Nixpacks. Перенести сохранившиеся файлы и выдать права пользователю приложения. Каталог `job-application-files` должен оставаться закрытым обработчиками Payload.
4. Запустить сначала под временным доменом/через локальное сопоставление доменов. Проверить `/`, `/shop`, `/admin`, каталог, вход покупателей и администраторов, настройки, изображения и кабинеты. Восстановленные записи не доказывают наличие всех оригинальных изображений.
5. После проверки переключить DNS для `10coffee.ru` и `shop.10coffee.ru`, выпустить HTTPS и проверить оба хоста. Проверить внешние callback и webhook адреса.

## Перед возобновлением продаж

Получить актуальные данные МС и ЮKassa из сохранившихся внешних кабинетов, если доступ к ним есть. Сверить актуальный последний номер заказа с `order_number_seq`, чтобы старый локальный счётчик не выдавал номера уже существующих заказов. Не запускать повторную выгрузку старых заказов или массовый импорт без сверки. Данные после 21 августа из найденной локальной БД не восстанавливаются этой копией.

Заново проверить способы доставки и оплаты, провести согласованный тест оформления. Включать МС, платёжные и почтовые интеграции после проверки их актуальных настроек. Секреты утраченного сервера нельзя восстановить из Git; доступность отдельных локальных настроек проверяется отдельно без публикации их значений.

## Резервирование нового размещения

Настроить автоматический backup PostgreSQL с копией вне сервера, архив файлов и отдельный backup Coolify с сохранением ключа восстановления. Проверить восстановление копии в отдельную БД. Снимок/том внутри единственного сервера не заменяет внешнюю копию.

## Локальные инструменты

* `node scripts/recovery-inventory.mjs` — сведения о локальной БД только на чтение, без вывода персональных данных и секретов.
* `node scripts/recovery-backup.mjs НОВЫЙ_КАТАЛОГ` — новый custom-дамп и проверка списка. Требуются `pg_dump` и `pg_restore`, путь можно задать в `PG_BIN_DIR`.
* `node scripts/recovery-verify.mjs ПУТЬ/site.dump` — проверка SHA256 и восстановление в новую уникальную локальную БД. Существующие БД не заменяются; проверочная БД сохраняется.
* `node scripts/recovery-check-app.mjs КАТАЛОГ_КОПИИ migrate-status` и `... build` — проверка текущего кода на восстановленном клоне. Интеграции отключены, исходная база и исходный дамп не изменяются.
* `node scripts/recovery-http-check.mjs КАТАЛОГ_КОПИИ` — проверка собранного сайта на восстановленной тестовой БД; временный сервер останавливается по завершении.
* `node scripts/recovery-salvage-media.mjs НОВЫЙ_КАТАЛОГ` — сверка оригинальных имён из БД с рабочими файлами и доступной историей Git. Найденные файлы копируются отдельно.
